CPUE derivation: CPUEL product vs HL-derived

Author

Einar Hjörleifsson

Published

June 1, 2026

Modified

July 1, 2026

1 Preamble

ICES provides a pre-computed CPUE-by-length product (CPUEL) for a subset of DATRAS surveys. This document compares it against CPUE derived directly from the raw HH and HL tables and identifies three structural problems with the CPUEL product.

Atlantic cod (Gadus morhua, AphiaID 126436) is used as a concrete species throughout. The structural findings apply across species.

2 Status: Superseded

June 2026: This document remains as a reference for the three structural problems in the ICES CPUEL product. However, guidance has been updated.

Recommended approach: Use dr_con("HL_standardised") |> filter(type == "length") directly. This pre-computed table covers all 29 DATRAS surveys, addresses all three problems documented here, and is the foundation for IMBUS D2.3 deliverables.

For updated guidance see the obus catch products vignette.

2.1 The HL_standardised product — Recommended for all CPUE work

The IMBUS D2.3 data product is HL_standardised — a pre-computed standardised HL table covering all 29 DATRAS surveys and all species. It is accessible via dr_con("HL_standardised") and can be filtered directly to length-frequency rows without needing to work through the raw HH and HL tables.

library(obus)

# Ready-to-use — no CPUE arithmetic needed. Use this for all new work.
cod <- dr_con("HL_standardised") |>
  filter(type == "length", latin == "Gadus morhua") |>
  collect()

Key properties:

  • Full haul key (.id): Survey, Year, Quarter, Country, Platform, Gear, StationName, HaulNumber — unambiguous identification
  • Valid hauls only (HaulValidity == "V" pre-applied)
  • Not zero-filled at source: use dr_catch_by_haul() or dr_expand_length() downstream
  • p_females column retains sex composition without a separate sex grouping dimension
  • All surveys (29 total vs 8 in CPUEL)

The three problems with CPUEL documented below do not apply to HL_standardised.

3 Historical reference: dr_cpue_length()

Note: dr_cpue_length() is superseded by the dr_HL_standardised() pipeline. The function below is preserved as documentation of how the derivation works.

The three problems documented below all stem from using the CPUEL product. An earlier recommended alternative was to derive CPUE directly from HH and HL using the dr_cpue_length() helper below. The function:

  • Uses the full .id haul key (Survey:Year:Quarter:Country:Platform:Gear:StationName:HaulNumber), avoiding the ambiguity of CPUEL’s shortened key.
  • Zero-fills via HH |> left_join(HL), so every valid haul appears in the output — hauls with no catch for the target species get length_mm = 0, n_haul = 0, n_hour = 0.
  • Outputs the minimum necessary columns: .id, length_mm, n_haul, n_hour. Haul metadata (position, gear, date, etc.) is retrieved by joining the output to dr_con("HH") on .id.
  • Works lazily within the dplyr/DuckDB framework — call collect() on the result when ready to pull into memory.
#' Derive length-frequency CPUE from HH and HL
#'
#' @param hh  Lazy HH table, pre-filtered to the target survey/year/quarter
#'            and restricted to valid hauls (HaulValidity == "V").
#' @param hl  Lazy HL table, pre-filtered to a single target species
#'            (e.g. filter(aphia == 126436)).
#' @param collapse_sex   If TRUE (default), sum across sex levels.
#'            Set FALSE to retain sex as a grouping dimension.
#' @param collapse_stage If TRUE (default), sum across DevelopmentStage levels.
#'            Set FALSE to retain developmental stage as a grouping dimension.
#'
#' @return A lazy dplyr/DuckDB table with columns:
#'   .id, length_mm, [sex], [DevelopmentStage], n_haul, n_hour.
#'   Zero-catch hauls appear as a single row with length_mm = 0, n_haul = 0,
#'   n_hour = 0. Join to dr_con("HH") on .id to retrieve haul metadata.
dr_cpue_length <- function(hh, hl,
                           collapse_sex   = TRUE,
                           collapse_stage = TRUE) {
  group_vars <- c(".id", "length_mm")
  if (!collapse_sex)   group_vars <- c(group_vars, "sex")
  if (!collapse_stage) group_vars <- c(group_vars, "DevelopmentStage")

  hh |>
    select(.id, HaulDuration, DataType) |>
    left_join(
      hl |>
        dr_add_length_mm() |>
        select(.id, length_mm, sex, DevelopmentStage,
               NumberAtLength, SubsamplingFactor),
      by = ".id"
    ) |>
    dr_add_n_and_cpue() |>
    group_by(across(all_of(group_vars))) |>
    summarise(
      n_haul = sum(n_haul, na.rm = TRUE),
      n_hour = sum(n_hour, na.rm = TRUE),
      .groups = "drop"
    ) |>
    mutate(
      length_mm = coalesce(length_mm, 0),
      n_haul    = coalesce(n_haul,    0),
      n_hour    = coalesce(n_hour,    0)
    )
}

5 Problem 1 — Ambiguous haul key

The CPUEL output uses a shortened haul key — Survey:Year:Quarter:Platform:Gear:HaulNumber — omitting Country and StationName. The full key used in HH and HL is Survey:Year:Quarter:Country:Platform:Gear:StationName:HaulNumber. In any year-quarter where two different hauls share the same short key (same vessel, same haul number, but different station), CPUEL cannot identify which haul a record belongs to.

Across all valid HH records, 2439 unique short keys each resolve to more than one full .id (covering 4922 hauls):

Code 
dr_con("HH") |>
  filter(HaulValidity == "V") |>
  mutate(.id2 = paste(Survey, Year, Quarter, Platform, Gear, HaulNumber, sep = ":")) |>
  distinct(.id, .id2) |>
  count(.id2) |>
  filter(n > 1) |>
  count(n, name = "n_ambiguous_keys") |>
  collect() |>
  rename(`Full .id per short key` = n, `Number of ambiguous short keys` = n_ambiguous_keys) |>
  knitr::kable()

A concrete example — two valid BITS hauls sharing the same short key, distinguished only by StationName, with similar positions:

           ShootLatitude, ShootLongitude) |>
  collect() |>
  group_by(.id2) |>

CPUEL does contain ShootLatitude and ShootLon, which might appear to offer a way to disambiguate. However, as the example above shows, hauls that differ only in StationName can have near-identical positions. Lat/lon is not a reliable join key.

The consequence for users is not that CPUEL’s CPUE values are wrong — ICES computes CPUEL internally using the full key, then truncates the output. The problem arises when users try to join CPUEL back to HH (e.g. to retrieve depth, gear parameters, or exact position): for any of the 2,400+ ambiguous short keys, the join is indeterminate and may pull metadata from the wrong haul.

For NS-IBTS Q1 2025 specifically, 49 short keys resolve to 2 hauls each (98 hauls total). CPUEL presents 312 distinct short keys; the correct count is 361 distinct hauls. Of those 98 hauls with duplicated keys, 66 had cod catch. The CPUE totals happen to agree because CPUEL computes internally with the full key and only truncates the output — but any attempt to join CPUEL records back to HH on the short key to retrieve metadata (position, depth, gear) will return wrong results for those 49 ambiguous keys.

6 Problem 2 — Non-valid hauls included

CPUEL does not filter by HaulValidity. For BITS, a comparison across all years shows:

Code 
haul_coverage <- map_dfr(cpuel_surveys, function(sv) {
  cpuel_h <- dr_con("CPUEL") |>
    filter(Survey == sv) |>
    mutate(.id2 = paste(Survey, Year, Quarter, Platform, Gear, HaulNumber, sep = ":")) |>
    distinct(.id2) |>
    collect() |>
    pull(.id2)

  valid_h <- dr_con("HH") |>
    filter(Survey == sv, HaulValidity == "V") |>
    mutate(.id2 = paste(Survey, Year, Quarter, Platform, Gear, HaulNumber, sep = ":")) |>
    distinct(.id2) |>
    collect() |>
    pull(.id2)

  tibble(
    Survey                = sv,
    `CPUEL keys`          = length(cpuel_h),
    `Valid HH keys`       = length(valid_h),
    `Extra in CPUEL`      = length(setdiff(cpuel_h, valid_h)),
    `Missing from CPUEL`  = length(setdiff(valid_h, cpuel_h))
  )
})

haul_coverage |> knitr::kable()

Only ROCKALL has a clean match. The Extra in CPUEL hauls are the critical concern — these are keys present in CPUEL but absent from valid HH, meaning CPUEL contains catches from hauls that should be excluded. For BITS 2023 cod specifically, this inflates the total CPUE:

7 Problem 3 — Sex aggregated to NA

CPUEL groups by (haul × length class) and sums across sex, setting the field to NA. This is the case for 7 of the 8 CPUEL surveys. EVHOE is the only exception, retaining M, F, and U — though it also has many NA rows for species where sex is not recorded.

Code 
dr_con("CPUEL") |>
  count(Survey, sex) |>
  collect() |>
  pivot_wider(names_from = sex, values_from = n, values_fill = 0) |>
  arrange(Survey) |>
  knitr::kable()

For any survey other than EVHOE, using CPUEL means all sex-at-length information is lost. Using dr_cpue_length(..., collapse_sex = FALSE) preserves whatever sex information was recorded in HL.

The row-count consequence: for NS-IBTS Q1 2025 cod, HL records both M and F at the same length class in 3 (haul × length) combinations. CPUEL merges these pairs into single NA rows, producing 3 fewer rows than the sex-resolved HL derivation. Per-haul totals are identical:

8 Summary

Problem Description Remedy
Ambiguous haul key CPUEL omits Country and StationName from the output key. 2,400+ short keys resolve to multiple full hauls in HH. Joining CPUEL to HH for metadata retrieval is unreliable for those hauls. Use full .id key via dr_cpue_length()
Non-valid hauls included CPUEL does not filter by HaulValidity. 94% of the extra-in-CPUEL BITS hauls were already non-valid when CPUEL was computed — staleness explains only 4%. Filter HH to HaulValidity==‘V’ before calling dr_cpue_length()
Sex aggregated to NA 7 of 8 CPUEL surveys have Sex=NA for all records. Sex-at-length is unrecoverable from CPUEL. Only EVHOE retains M/F/U. Use collapse_sex = FALSE in dr_cpue_length()

Guidance: For new CPUE-by-length analysis, use dr_con("HL_standardised") |> filter(type == "length") directly. It covers all 29 DATRAS surveys with consistent methodology. Archive CPUEL for historical reference only.
