D2.3 — IMBUS Integrated Data Product Specification

IMBUS Deliverable D2.3 · Work Package 2

Author

Einar Hjörleifsson (subcontracted to DTU Aqua)

Published

August 1, 2026

Modified

July 1, 2026

Project: IMBUS — Implementing More and Better Use of ICES Survey Data Deliverable: D2.3 — Integrated data product (parquet files) Work Package: WP2 — User requirements, data formats and meta-data Status: DRAFT Due: Month 12 (August 2026)

1 Executive Summary

This document is the technical specification for the IMBUS integrated data product (D2.3, Type: DATA). It defines the proposed column names, file formats, data tier structure, and design principles for the standardised representation of the ICES DATRAS bottom trawl survey exchange tables.

The D2.3 product itself — the parquet files — is hosted at https://heima.hafro.is/~einarhj/datras/ (interim; transfer to the ICES open access portal is planned under D2.4). Long-term sustainability is handled by WP5: D5.3 (ICES, M18) formally integrates the IMBUS data products and the {obus} codebase into the ICES DATRAS R library and ICES web services. The raw DATRAS data supply that feeds D2.3 is formalised in D5.1 (ICES, M6).

The principal design decisions are:

  1. Unified column naming. A single, consistent set of column names is applied across all record types and surveys, regardless of API source or era. The full field mapping is documented in D2.2 §2.
  2. Parquet-based distribution. HH, HL, and CA exchange tables are stored as columnar parquet files enabling fast, column-selective querying without full downloads.
  3. Sentinel value removal. The DATRAS convention of using −9 for missing values is replaced with proper missing-value encoding.
  4. Species resolution via WoRMS AphiaID. Historical species codes (ITIS TSN, NODC) are mapped to current WoRMS AphiaIDs for cross-era joins.
  5. Unique haul identifiers. An 8-field composite key (.id) uniquely identifies each haul across all surveys, years, and countries.
  6. A standardised HL product. A unified standardised representation of the HL exchange table — HL_standardised.parquet — resolves the unit ambiguities, DataType dependencies, and sex-recording heterogeneity of raw HL into a single clean, self-contained product covering all valid hauls across all 29 surveys.
  7. DataType-corrected CPUE. A transparent, reproducible calculation pathway raises raw exchange data to catch-per-unit-effort, handling all DataType variants correctly.

The specification is implemented in the R package {obus} (https://github.com/einarhjorleifsson/obus). {obus} is explicitly experimental and serves as the proof-of-concept implementation for the WP2 period; its functionality is intended to be upstreamed into the official icesDatras R package under WP5/D5.3 (M18).

2 Background and Purpose

This document is the technical specification for D2.3, the IMBUS integrated data product. It should be read alongside D2.2 (Data Formats and Metadata), which provides the field-by-field documentation of the current DATRAS exchange format — the reference for the naming conventions, field descriptions, and known issues that underpin the design decisions here.

The IMBUS project (Sep 2025 – Aug 2027) is a 24-month EU-funded initiative to improve use of ICES trawl survey data. WP2 is responsible for data standardisation. The four WP2 objectives are:

  1. Assess user requirements. (Addressed in D2.1, April 2026.)
  2. Develop a data format for WP3–5 products.
  3. Generate meta-data descriptions.
  4. Process current DATRAS data into the new format.

D2.3 delivers on objectives 2 and 4 — the standardised data product. D2.2 delivers objective 3 — the metadata documentation.

2.1 Scope

In scope:

  • Proposed standardised column names and their mapping from current DATRAS names.
  • Parquet file format, hosting, and access via the {obus} R package.
  • Unique haul identifier (.id) construction.
  • Design and schema of the standardised HL product (HL_standardised).
  • Data tier structure (Tier 0 raw / Tier 1 standardised).
  • Calculation pathways from raw exchange data to CPUE-by-length and exploratory CPUE-by-age.
  • {obus} interim status and transition path to icesDatras (D5.3).

Out of scope:

  • Field-by-field documentation of the current DATRAS exchange format — see D2.2.
  • Official CPUEA and age-based survey indices (ICES Datacenter products).
  • Deployment to the ICES open access portal — subject of D2.4.
  • Per-survey metadata fact sheets — addressed separately under user requirement UR-Q1.

3 IMBUS Proposed Data Formats — D2.3 Product Specification

Deliverable D2.3 scope. This document is the technical specification for the IMBUS integrated data product (D2.3, Type: DATA, due M12). It defines the proposed column names, file formats, data tier structure, and design principles. The D2.3 product itself — the parquet files — will be hosted on the ICES open access portal under D2.4 (M12). The current interim location is https://heima.hafro.is/~einarhj/datras/.

Long-term sustainability is handled by WP5: D5.3 (ICES, M18) formally integrates the IMBUS data products and the {obus} codebase into the ICES DATRAS R library and ICES web services, ensuring D2.3 has an institutional home beyond the project period. The raw DATRAS data supply that feeds D2.3 is formalised in D5.1 (ICES, M6).

3.1 Standardised Data Formats

3.1.1 Harmonised variables

The IMBUS product uses standard column names throughout (see D2.2 — Current Issues: column naming). Where data originate from the legacy XML API, an automatic translation step maps legacy to standard names using the field dictionary dr_lookup_fields. Fields with no standard equivalent retain their original names. The full mapping (~292 fields) is available in the dr_lookup_fields data object in {obus} and in the companion DATRAS Field Reference.

Interim names. Two fields — sex and aphia — use IMBUS canonical names that deviate from the (inconsistent) ICES “new” names, as a temporary measure pending resolution by the ICES Datacenter. See D2.2 — IMBUS interim canonical names.

Additional standardisation steps applied to all exchange tables:

  • Sentinel value removal. The DATRAS convention of using −9 for missing values is replaced with proper missing-value encoding (NA).
  • Species resolution. Historical species codes (ITIS TSN, NODC) are mapped to current WoRMS AphiaIDs (aphia) for cross-era joins.
  • Unique haul identifier. An 8-field composite key (.id) uniquely identifies each haul across all surveys, years, and countries.

3.1.2 Unique Haul Identifier

A composite key constructed from eight fields uniquely identifies each haul:

.id = Survey : Year : Quarter : Country : Platform : Gear : StationName : HaulNumber

Example: "NS-IBTS:2023:1:NL:58G2:GOV:18:27"

This is the recommended join key for all operations across the IMBUS product suite. A shorter 6-field key (omitting Country and StationName) is also available for comparison with the ICES CPUEL derived product, which omits those two fields. The 6-field key is ambiguous — more than 2,400 short keys match more than one haul in the full dataset — and is provided only for backward-compatibility diagnostics, not for production use.

3.1.3 The standardised HL product: design rationale

The raw DATRAS HL exchange table mixes three distinct kinds of information in every row: length-frequency measurements, haul-level totals, and subsampling metadata. On top of this, several field values cannot be interpreted without context from other fields or from a separate table: the length unit depends on a code field (LengthCode); the meaning of a count depends on the haul’s DataType and HaulDuration (both in HH, not HL); and species are identified by numeric code rather than name. The result is that every analyst must re-derive units, joins, and scaling from scratch before any analysis can begin.

The IMBUS standardised HL product resolves these ambiguities once, producing a clean, self-contained table where every column has a single unambiguous meaning. Four design decisions shape the result.

Two counting paths, one table. The HL table contains two independent records of the same catch: length-frequency measurements (NumberAtLength) and haul-level totals (TotalNumber). Both are scaled to consistent units — numbers per haul (n_haul) and numbers per hour of towing (n_hour) — and retained in a single table, distinguished by a type column:

  • type = "length" — counts derived from NumberAtLength, one row per species × length class per haul. Used for length-structured analyses: length-frequency distributions, age-length keys, year-class tracking.
  • type = "haul" — counts derived from TotalNumber, one row per species per haul. Used for haul-level totals, biomass indices, and as a cross-check on the length-derived totals.

Keeping both paths in a single table, rather than two separate files, means every caught species is always present (via its type = "haul" row) even when it was never individually measured at length. The type flag makes the distinction explicit: any downstream analysis using n_haul or n_hour must filter on type first.

Sex as a proportion. Raw HL records the same haul × species × length class in multiple rows split by sex. Rather than carrying sex as a row-splitting dimension, the standardised product collapses sex into a single derived column p_females — the proportion of individually sexed fish at each length class that were female. Female and male counts can be recovered by multiplying n_haul or n_hour by p_females and 1 − p_females respectively. p_females is absent when no fish in the group were individually sexed.

DevelopmentStage dropped. Across the 2010–2020 exchange data, 99.7% of records carry no developmental stage code; the remainder are summed over during aggregation in any case. Users who need to work with developmental stage should access the raw HL parquet directly.

StandardSpeciesCode / BycatchSpeciesCode not carried through. These haul-level flags from HH record what a vessel was obligated to report for each haul. They are not carried into the standardised product but remain available via a join to HH on .id.

Tier 0 — Raw exchange parquets (hosted)
  HH.parquet, HL.parquet, CA.parquet, LT.parquet

  For: expert users, QC, full-fidelity reproduction.

Tier 1 — Standardised HL product (hosted)

                            Generated by: dr_HL_standardised(dr_con("HH"), dr_con("HL"),
                                                             haulval = "V")
                            Accessed via: dr_con("HL_standardised")
  For: all survey-analysis users; the recommended starting point for CPUE, indices,
       length distributions, and biomass workflows.

Official ICES derived products (accessible via dr_get())
  CPUEA / IDX   Age-based CPUE and indices; ICES Datacenter products.
  For: formal stock assessment; not produced by IMBUS.

3.2 File Formats Used

3.2.1 Parquet

The IMBUS product distributes HH, HL, CA, and the standardised HL as columnar parquet files. Parquet enables fast, column-selective querying without downloading the full table — a critical advantage given that HL alone contains tens of millions of rows across all surveys and years.

Table URL
HH https://heima.hafro.is/~einarhj/datras/HH.parquet
HL https://heima.hafro.is/~einarhj/datras/HL.parquet
CA https://heima.hafro.is/~einarhj/datras/CA.parquet
HL_standardised https://heima.hafro.is/~einarhj/datras/HL_standardised.parquet

These files are readable by any tool that supports the parquet format or the DuckDB query engine: R, Python, Julia, DBeaver, and others.

3.2.2 Data access via {obus}

The {obus} R package provides two access modes:

Lazy parquet connection (recommended for large queries). A connection to a parquet file returns a lazy query object. Filters are pushed down to the file; only the requested rows and columns are transferred into memory:

library(obus)
library(dplyr)

# Length-frequency CPUE — filter to length rows and desired species/survey
cod_lengths <- dr_con("HL_standardised") |>
  filter(type == "length", Survey == "NS-IBTS", latin == "Gadus morhua") |>
  collect()

# Haul-level catch totals
cod_hauls <- dr_con("HL_standardised") |>
  filter(type == "haul", Survey == "NS-IBTS", latin == "Gadus morhua") |>
  collect()

Full download via dr_get(). Downloads and collects an entire table into memory, optionally filtered via the legacy ICES XML API. Appropriate for smaller, targeted queries.

3.2.3 {obus}: interim status and transition path

{obus} is explicitly experimental (lifecycle status: experimental) and is best understood as the proof-of-concept implementation for the WP2 data standardisation work. It is not intended to be a permanent, standalone R package. Its role within the IMBUS project lifecycle is:

  1. Proof-of-concept. Provide a working, validated implementation of the naming conventions, DataType arithmetic, parquet access, and CPUE pathways described in this document during the WP2 delivery period (M1–M12).
  2. D2.3 delivery vehicle. Serve as the primary means of accessing the D2.3 data product (parquet files) while those files are hosted on the interim server.
  3. Design feedback loop. Accumulate community experience and feedback that directly informs what is worth upstreaming into the official ICES infrastructure.

{obus} builds on, rather than replaces, the official icesDatras package — it imports icesDatras and delegates XML-source downloads to it. The added value is the parquet/DuckDB access layer, unified column naming, DataType-aware derived fields, and the quality-check family.

Intended trajectory. Under WP5/D5.3 (ICES, M18), the functionality proven in {obus} is a candidate for integration into the official ICES DATRAS R library (icesDatras), alongside migration of the parquet files to ICES-managed infrastructure. The naming-convention mapping, the DataType arithmetic, and the composite haul key (.id) are the most transferable elements.

3.3 Updated Meta-data Descriptions

The IMBUS standard names and field definitions described in D2.2 §2 and this document constitute an updated meta-data description for the DATRAS exchange tables. The companion document DATRAS Field Reference provides complete field reference tables for all HH, HL, CA, and LT fields, including types, units, valid values, and a drop-or-derive quick reference.

Per-survey meta-data fact sheets (coverage, gear history, time-series breaks, QC history) are not produced by D2.3. These are addressed separately under user requirement UR-Q1.

3.4 Standardised Code for Processing DATRAS Data

WP2 does not generate new CPUE data series. Instead, it provides transparent, reproducible code that any user can apply to the standardised exchange tables to generate CPUE on demand.

3.4.1 Data flow

DATRAS database
      │
      ▼
Raw exchange download    ← getDATRAS() (legacy XML API)
      │
      ▼
Type normalisation       ← dr_settypes(): column types enforced; −9 → NA
Column renaming          ← dr_translate(): legacy → standard names
      │
      ▼
Raw parquets (server)    ← HH.parquet / HL.parquet / CA.parquet
      │
      ▼
Standardised HL          ← dr_HL_standardised(dr_con("HH"), dr_con("HL"), haulval="V")
  (server)               ← HL_standardised.parquet
      │
      ▼
User analysis            ← dr_con("HL_standardised") |> filter(type == ...) |> collect()
                         → dr_catch_by_haul() / dr_expand_length() for zero-filling

Stages 1–3 are handled once by the data provider (currently Einar Hjörleifsson; ICES from D2.4/D5.3). The standardised HL is regenerated whenever the raw parquets are updated. Users interact from stage 4 onward.

3.4.2 {obus} helper functions

Function Description
dr_add_id() Construct the 8-field composite haul key .id
dr_add_length_cm() Standardise LengthClass to centimetres, accounting for LengthCode
dr_add_length_mm() Standardise LengthClass to millimetres
dr_add_n_and_cpue() Compute DataType-corrected n_haul and n_hour from NumberAtLength
dr_HL_standardised() Build the standardised HL table on demand from raw HH + HL
dr_catch_by_haul() Zero-filled haul totals from the standardised HL
dr_expand_length() Zero-filled complete length grid from the standardised HL
dr_check_*() Quality-check family; returns a report tibble without throwing errors
dr_get_areas() Survey strata as a spatial object
dr_assign_area() Spatial join of haul positions to survey strata

3.4.3 CPUE calculation pathway

CPUE-by-length requires five steps:

  1. Filter valid hauls: retain only hauls with HaulValidity = "V". (Pre-applied in HL_standardised.)
  2. Filter standard species records: retain SpeciesValidity = "1".
  3. Join DataType and HaulDuration from HH to HL on .id. (Pre-applied.)
  4. Compute n_haul and n_hour using the DataType-appropriate formula. (Pre-applied.)
  5. Aggregate across sex and species category. (Pre-applied; sex summarised as p_females.)

For users working from dr_con("HL_standardised"), steps 1, 3, 4, and 5 are already complete. The remaining user step is to filter SpeciesValidity = "1" and select the survey, species, and year range of interest.

The DataType-aware arithmetic that underpins step 4 handles the three submission conventions:

DataType Meaning n_haul n_hour
R (raw) Sorted, possibly sub-sampled NumberAtLength × SubsamplingFactor (NA → 1) n_haul × 60 / HaulDuration
S, P (bulk / size-stratified) Sub-sampled; SubsamplingFactor always > 1 NumberAtLength × SubsamplingFactor n_haul × 60 / HaulDuration
C (CPUE already) Pre-raised to 1-hour equivalent NumberAtLength × SubsamplingFactor × HaulDuration / 60 NumberAtLength × SubsamplingFactor

HaulDuration is in minutes throughout. CPUE = catch in numbers per one hour of towing.

3.4.4 Zero observations and zero-fill

A CPUE value of zero means the species was absent from that haul but was caught by at least one vessel in the same survey × year × quarter. Zero rows are required for unbiased abundance indices: when aggregating CPUE across hauls within a stratum, hauls where the species was not observed must contribute a zero — omitting them inflates the mean.

HL_standardised contains only observed rows (no zeros). Zero-filling is applied downstream by dr_catch_by_haul() and dr_expand_length(), which add an explicit zero row for every haul in a Survey × Year × Quarter where a given species was absent. This matches the convention used by the official ICES CPUE data products.

A note on phantom zeros. The pooled zero-fill approach can produce phantom zeros for hauls that were never required to record a given species. The DATRAS HH table records what each vessel was obligated to report (StandardSpeciesCode, BycatchSpeciesCode), and the official ICES index methodology uses these flags for a further haul-selection step. The {obus} zero-fill functions follow the DATRAS CPUE product convention and do not implement this additional filter. Users building formal survey indices should apply haul-selection using the HH flags directly.

3.5 The HL_standardised product

HL_standardised.parquet is the delivered Tier 1 standardised HL product. It covers all 29 DATRAS surveys, valid hauls only, and is derived directly from the raw HH and HL parquets by dr_HL_standardised(dr_con("HH"), dr_con("HL"), haulval = "V"). It is accessible via dr_con("HL_standardised").

Schema:

Column Type Unit Notes
.id chr — 8-field composite haul key
Survey chr — Survey acronym
Year int — Survey year
Quarter int — Survey quarter
aphia int — Resolved WoRMS AphiaID
latin chr — WoRMS accepted Latin name
species chr — Common (vernacular) name
type chr — "length" or "haul" (see design rationale)
length_mm dbl mm Standardised length in mm; NA for type = "haul" rows
length_cm dbl cm Standardised length in cm; NA for type = "haul" rows
accuracy dbl cm Length measurement resolution; NA for type = "haul" rows
n_haul dbl count DataType-corrected numbers per haul
n_hour dbl count/hr DataType-corrected numbers per hour of towing
w_haul dbl g Catch weight per haul; NA for type = "length" rows and when weight not recorded
w_hour dbl g/hr Catch weight per hour; NA as for w_haul
p_females dbl proportion Fraction of sexed individuals that are female; NA when no sexing data
SpeciesValidity chr — Record type code — filter to "1" before analysis

Key derivation decisions:

  • Valid hauls only. HL is joined to HH records where HaulValidity = "V". Invalid hauls are excluded.
  • Length records only in type = "length" rows. Rows where LengthClass is absent (totals-only and presence/absence record types) are excluded from type = "length" rows.
  • SpeciesValidity retained (interim). No filter on SpeciesValidity is applied during product derivation; it is retained so that records of different types co-occur visibly. For most analyses, filter to SpeciesValidity = "1" after collecting. The correct handling of non-"1" codes is an open question pending clarification from the ICES Datacenter.
  • No zero-fill. The product contains observed rows only. Zero-filling is applied by the user downstream via dr_catch_by_haul() or dr_expand_length() as needed.

Comparison with the ICES CPUEL product (for length-frequency CPUE):

ICES CPUEL HL_standardised (type = “length”)
Surveys covered 8 All 29
Haul validity filter None applied Valid hauls only
Haul key 6 fields (2,400+ ambiguous) Full .id (8 fields; unambiguous)
SpeciesValidity filter Pre-filtered to "1" Retained — user filters after collecting
Sex retained NA for 7 of 8 surveys Collapsed to p_females
Weight Not included w_hour available from type = "haul" rows
Species identifier Scientific name string Latin name + common name + AphiaID
Zero-catch hauls Present (added by DATRAS) Not included — add downstream

See DATRAS/cpue_derivation.qmd for a detailed comparison of the two approaches.

3.6 Exploratory CPUE-by-age

Age-disaggregated CPUE is achievable from the exchange tables but involves analytical choices that the IMBUS standardisation does not prescribe:

Official CPUEA Exploratory CPUE-by-age
ALK source ICES expert-group agreed User-defined from CA
Pooling level Survey/species specific User’s choice
Plus-group handling Agreed convention User’s choice
Appropriate for Formal stock assessment Research, exploration
Accessible via dr_get("CPUEA", ...) User pipeline on HL_standardised + CA

The general pathway: (1) use HL_standardised filtered to type = "length" as the CPUE-by-length input; (2) construct an age-length key from CA; (3) apply the ALK to the length CPUE; (4) aggregate across hauls. Step 1 is directly satisfied by dr_con("HL_standardised"), substantially reducing the entry barrier for this approach.

A pre-computed CA_raised.parquet product (one row per .id × aphia × age) has been proposed as a complement to HL_standardised. Its design requires input from WP4 on ALK pooling level, plus-group threshold, and area-pooled CA rows; see Appendix 2 for the current schema sketch.

4 Discussion and Conclusions

The D2.3 product specification addresses a long-standing barrier to broader use of ICES bottom trawl survey data: the complexity of deriving analysis-ready products from the raw DATRAS exchange format. The raw format is rich and flexible — necessarily so, to accommodate the diversity of national sampling protocols across 29 surveys — but that same flexibility imposes a substantial entry cost on users who simply want species-level catch-per-unit-effort for a given survey and year. Every analyst has historically had to resolve unit ambiguities, handle DataType-conditional arithmetic, and manage zero-filling independently, with no assurance of consistency across research groups.

A single standardised product for the majority of use cases. The HL_standardised parquet delivers what most users need in one file: DataType-corrected counts at length and at the haul level, species names resolved, lengths in a single consistent unit, and sex summarised in a recoverable form. The type column cleanly separates the two counting paths that raw HL conflates, so users working with length distributions filter to type = "length", while users working with haul totals or biomass filter to type = "haul" — without needing to understand the underlying DataType conventions or subsampling arithmetic.

Coverage and quality are substantially improved relative to the ICES CPUEL product. The official CPUEL product covers 8 of 29 surveys and does not apply a haul-validity filter. HL_standardised covers all 29 surveys, filters to valid hauls, and provides an unambiguous 8-field join key. For the 8 surveys where CPUEL exists, WP2’s analysis confirmed that the HL_standardised CPUE series are consistent with CPUEL (modulo the known structural differences), validating the derivation.

The design makes an implicit contract explicit. The raw HL table contains two independent records of the same catch — length-frequency measurements and haul-level totals — mixed in the same rows without any formal distinction. The standardised product separates these into two row types with consistent column names and units. When the two paths agree, users can proceed with confidence; a persistent divergence points to a genuine data inconsistency in the original submission, flagged by the dr_check_totalno() quality function.

Known limitations. Three open items require acknowledgement. First, the zero-fill convention — pooling species across all hauls in a survey × year × quarter — matches the DATRAS CPUE product convention but can produce phantom zeros for hauls never required to record a given species. Formal index calculations should apply the additional haul-selection step using the StandardSpeciesCode and BycatchSpeciesCode flags in HH. Second, the pre-computed CA_raised product (age-disaggregated abundance) has not been produced; its design depends on WP4 input on ALK pooling conventions that has not yet been finalised. Third, the parquet files remain on an interim personal server; transfer to ICES-managed infrastructure is pending D2.4 and D5.3.

Sustainability and reproducibility. HL_standardised is derived from the raw exchange parquets using a single documented function call (dr_HL_standardised()). Any user can reproduce the product from the Tier 0 parquets using open code, without any intermediate files. The {obus} package is explicitly experimental; its functionality, together with the parquet files, is a candidate for integration into the official icesDatras R package and ICES-managed infrastructure under WP5/D5.3 (M18). At that point the D2.3 products will have an institutional home within ICES that ensures their long-term availability and maintenance.

5 Further Work

The following items are open as of the date of this document:

  1. Parquet hosting. The current parquet files are on a personal server (heima.hafro.is). Transfer to the ICES open access portal is pending WP5/ICES coordination (D2.4).

  2. Integration into ICES infrastructure (D5.3). Per decisions from the 1 June 2026 IMBUS WP2-WP5 meeting, parquet/DuckDB functionality should be incorporated into the official ICES DATRAS R package rather than maintained as a separate tool. This is formally the scope of WP5 deliverable D5.3 (ICES, M18).

  3. CA_raised product. Age-disaggregated abundance (one row per .id × aphia × age) derived from ALK application to HL_standardised. Design requires input from WP4 on ALK pooling level, plus-group threshold, and area-pooled CA rows. See Appendix 2 for the current schema sketch.

  4. Haul-selection step for formal indices. The phantom-zero limitation described in §Standardised Code for Processing DATRAS Data requires implementing a haul-selection filter using StandardSpeciesCode / BycatchSpeciesCode. This is needed before HL_standardised can serve as a drop-in input for formal survey index calculation.

  5. Area standardisation. Mapping from haul positions to C-squares and ICES statistical divisions is partially implemented (dr_assign_area()) but the lookup helpers are not yet complete in {obus}.
